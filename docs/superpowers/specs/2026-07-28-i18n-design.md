# i18n Internationalization — Design Spec

## Overview

Add multi-language support to GitVitae, enabling users to configure translations for
both UI strings and portfolio content. The design follows GitVitae's "single source
of truth" philosophy — everything in `portfolio.config.yaml`.

## YAML Configuration Structure

Languages and translations live inside `portfolio.config.yaml` under a YAML block
per locale. The user edits one file, no external language files required.

## Architecture

### i18n Context (React Context API)

No external i18n library. A lightweight React Context provides the current locale,
a translation function `t(key)`, and the localized content object.

```
src/lib/i18n.ts
  - I18nContext
  - I18nProvider (wraps entire app in App.tsx)
  - useI18n()  → { locale, setLocale, t, content }
  - useT()     → shorthand for t()
```

### Language Detection Priority

1. `localStorage.getItem('locale')` — user's explicit choice
2. `navigator.language.split('-')[0]` — browser language, matched against configured languages
3. `config.defaultLanguage` — fallback

### Language Switching

- `setLocale(locale)` updates state + persists to `localStorage`
- No page reload needed — React re-renders with new translations
- `t(key)` resolves `key` against the current locale's `ui` object
- `content` provides the current locale's data fields

### Data Flow

```
portfolio.config.yaml
  → Vite (@rollup/plugin-yaml)
  → src/portfolio.config.ts (types + raw config)
  → I18nProvider (selects locale's content)
    → components read via useI18n().t() / useI18n().content
```

## Components

- Globe icon button in navbar, next to theme toggle
- Dropdown with language options from `config.languages`
- Selected language highlighted
- Selection saved to `localStorage`
- Closes on outside click
- Responsive — works on mobile

### I18nProvider (`src/lib/i18n.tsx`)

- Wraps entire app in `App.tsx` (around `Router`)
- Reads `localStorage` → `navigator.language` → `config.defaultLanguage`
- Provides `locale`, `setLocale`, `t()`, `content`
- `t(key)` does deep access: `t("ui.about") → content[locale].ui.about`

## Migration Strategy

### Backward Compatibility

The old flat format is detected by the absence of `defaultLanguage` field.
If detected, the system wraps all top-level content fields under an implicit `en` block
and treats the site as single-language English.

### Migration Script

`scripts/migrate-config.mjs` transforms an existing `portfolio.config.yaml`:

1. Read current config
2. Extract translatable fields (name, title, tagline, location, about, stats, skills,
   experience, projects, education, certifications, publications, testimonials,
   resumeUrl, resumeFileName)
3. Create `en` block with those fields + auto-generated `ui` block with defaults
4. Create `zh` block with empty fields for manual translation
5. Add `defaultLanguage: "en"` and `languages: [{code: "en", label: "English"}]`
6. Remove old top-level content fields
7. Write result, backup original to `portfolio.config.yaml.bak`

### Resume Generation

`scripts/generate-resume.mjs` updated to:
- Accept `--locale` argument (default: `config.defaultLanguage`)
- Read content from `config[locale]` for localized resume output
- Generates `public/resume.{locale}.json` and `public/resume.{locale}.md`

### check-config Script

`scripts/check-config.mjs` updated to validate:
- `defaultLanguage` is present and matches one of `languages` entries
- Each locale block has all required content fields
- No orphaned top-level content fields remain
